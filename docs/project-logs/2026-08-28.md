# Project Log — 2026-08-28

## Overview

Today's work focused on completing the transition to a dedicated centralized DHCP architecture, adding Internet connectivity to the lab, validating OSPF default-route propagation, and testing whether DHCP and Internet access continued working during an OSPF link failure.

The documentation was also updated to reflect the new topology and current design.

---

## 1. Added a Dedicated Server Network

A new server subnet was introduced:

```text
10.10.30.0/24
```

R2 was extended with a new interface for the server network:

```text
R2 eth2: 10.10.30.1/24
```

An Ubuntu Server VM named `DHCP01` was deployed:

```text
Hostname: dhcp01
Interface: ens3
IP: 10.10.30.10/24
Default gateway: 10.10.30.1
```

This server was created to replace the previous design where R1 acted as the centralized DHCP server.

---

## 2. Configured R2 to Advertise the Server Network in OSPF

The new server subnet needed to be reachable from R1 and R3.

An attempt was first made to configure the subnet using:

```text
set protocols ospf area 0 network '10.10.30.0/24'
```

VyOS rejected this because the existing OSPF configuration was already using interface-based configuration.

The correct configuration used the existing style:

```text
set protocols ospf interface eth2 area 0
```

Because `eth2` connects to DHCP01 and not another OSPF router, the interface was configured as passive:

```text
set protocols ospf interface eth2 passive
```

This means:

```text
Advertise 10.10.30.0/24 into OSPF: Yes
Send OSPF Hellos toward DHCP01:    No
Form an OSPF adjacency on eth2:    No
```

R1 and R3 were then able to learn the `10.10.30.0/24` server network dynamically.

## 4. Added GNS3 NAT for Internet Connectivity

DHCP01 could reach R2 but could not initially reach the Internet.

A GNS3 NAT node was added and connected to R2 `eth3`.

R2 `eth3` was configured as a DHCP client:

```text
set interfaces ethernet eth3 address 'dhcp'
```

The GNS3 NAT service assigned R2 an outside-facing address.

Observed during testing:

```text
R2 eth3: 192.168.42.234/24
GNS3 NAT gateway: 192.168.42.1
```

R2 also received a default route:

```text
0.0.0.0/0 via 192.168.42.1
```

R2 could then successfully ping:

```text
8.8.8.8
```

## 5. Configured Source NAT on R2

Although R2 could reach the Internet, DHCP01 still could not.

The problem was that packets from internal addresses such as:

```text
10.10.30.10
```

were leaving R2 without being translated.

Source NAT masquerading was configured on R2 for the entire internal lab address space:

```text
10.10.0.0/16
```

Conceptually:

```text
10.10.30.10
    |
    | Source NAT / Masquerade
    v
192.168.42.234
```

After source NAT was enabled, DHCP01 could successfully ping `8.8.8.8`.

## 10. Fixed Client Internet Access with OSPF Default-Route Origination

Even after R2 had Internet access and source NAT was working, PC1 and PC2 could not initially reach the Internet.

PC1 received a destination-unreachable response from R1.

The problem was that R1 and R3 did not know where to send traffic for unknown external destinations.

R2 already had:

```text
0.0.0.0/0 via 192.168.42.1
```

but that route had not been distributed to the rest of the lab.

R2 was configured to originate its default route into OSPF:

```text
set protocols ospf default-information originate
```

R1 and R3 then learned a default route through OSPF toward R2.

After this change:

```text
PC1 -> 8.8.8.8: Success
PC2 -> 8.8.8.8: Success
```

This completed end-to-end Internet connectivity for the client LANs.

## 11. Repeated OSPF Failover Test with DHCP and Internet Services

The direct R1-R3 link was disabled again to test the completed architecture.

R1 `eth2` was disabled:

```text
set interfaces ethernet eth2 disable
```

The normal path:

```text
PC1 -> R1 -> R3 -> PC2
```

changed to:

```text
PC1 -> R1 -> R2 -> R3 -> PC2
```

OSPF reconverged successfully.

During the failure:

```text
PC1 -> PC2: Success
PC2 -> PC1: Success
PC1 DHCP renewal: Success
PC2 DHCP renewal: Success
PC1 -> 8.8.8.8: Success
PC2 -> 8.8.8.8: Success
```

This verified that the backup path could support:

```text
Inter-LAN routing
Centralized DHCP
Internet connectivity
```

without manual intervention.

The direct R1-R3 link was then restored:

```text
delete interfaces ethernet eth2 disable
```

OSPF returned to the preferred lower-cost direct path.

## Key Lessons Learned

1. Routing reachability and application-level service behavior are separate troubleshooting layers.
2. DHCP relay allows a centralized server to serve multiple routed broadcast domains.
3. Packet capture can prove whether a client is actually sending DHCP traffic.
4. Passive OSPF interfaces allow a subnet to be advertised without forming an adjacency.
5. A default route only tells a router where to send unknown traffic; NAT is still required when private addresses access an upstream network.
6. A router's default route is not automatically known by other OSPF routers unless it is advertised.
7. Successful Internet access by IP does not imply DNS is working.
8. OSPF redundancy can preserve more than simple ping connectivity. It can also preserve routed infrastructure services such as DHCP and Internet access.
9. Service configuration should be validated before restart whenever possible.
10. Separating infrastructure services from routers produces a cleaner and more realistic enterprise-style design.
