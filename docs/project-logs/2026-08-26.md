# Centralized DHCP, DHCP Relay, and OSPF Failover Milestone
*26 August 2026*
Today I expanded the lab by implementing DHCP and then converting the design into a centralized DHCP architecture with DHCP relay.

## Local DHCP Testing

I first configured DHCP locally on both LANs to make sure I understood the basic DHCP process before introducing DHCP relay.

R1 provided DHCP for the PC1 LAN:

- Network: `10.10.10.0/24`
- Default gateway: `10.10.10.1`
- DHCP pool: `10.10.10.100 - 10.10.10.199`

PC1 successfully received:

```text
IP Address: 10.10.10.100/24
Gateway:    10.10.10.1
```

R3 was then configured as a DHCP server for the PC2 LAN:

- Network: `10.10.20.0/24`
- Default gateway: `10.10.20.1`
- DHCP pool: `10.10.20.100 - 10.10.20.199`

PC2 successfully received:

```text
IP Address: 10.10.20.100/24
Gateway:    10.10.20.1
```

This confirmed that DHCP was working correctly when the DHCP server was located on the same subnet as the client.

## Centralized DHCP Design

I then changed the design so that R1 became the centralized DHCP server for both LANs.

R1 now contains two DHCP scopes:

```text
LAN1
Network: 10.10.10.0/24
Pool:    10.10.10.100 - 10.10.10.199
Gateway: 10.10.10.1

LAN2
Network: 10.10.20.0/24
Pool:    10.10.20.100 - 10.10.20.199
Gateway: 10.10.20.1
```

The DHCP server configuration was removed from R3.

Instead, R3 was configured as a DHCP relay for the `10.10.20.0/24` network.

The reason a DHCP relay is required is that the initial DHCP Discover sent by a client is a broadcast. Routers normally do not forward broadcasts between subnets.

The DHCP relay on R3 receives PC2's DHCP broadcast and forwards the request as routed traffic to the DHCP server on R1.

The resulting design is:

```text
PC2
 |
 | DHCP broadcast
 v
R3
DHCP Relay
 |
 | Routed DHCP traffic
 v
R1
Central DHCP Server
```

R1 uses the relay information to determine that the request originated from the `10.10.20.0/24` network and therefore selects the LAN2 DHCP pool.

## DHCP Relay Troubleshooting

The first DHCP relay test failed.

PC2 displayed:

```text
Can't find dhcp server
```

I first verified basic connectivity from R3 to R1:

```text
R3 -> 10.10.10.1
```

The ping succeeded and R3 had a valid OSPF route to `10.10.10.0/24`, confirming that normal Layer 3 routing was working.

I then checked the DHCP server logs on R1.

The logs showed that R1 was actually receiving PC2's relayed DHCP Discover and generating a DHCP Offer. However, Kea produced the following error when attempting to return the response:

```text
Interface eth2/4 does not have any suitable IPv4 sockets open.
```

The DHCP server had initially been configured to listen only on:

```text
10.10.10.1
```

However, the best OSPF path from R1 back toward R3 used R1's `eth2` interface:

```text
R1 eth2: 10.10.100.9
```

Kea therefore needed a usable DHCP socket on that interface as well.

I resolved the issue by configuring the DHCP server to listen on both:

```text
10.10.10.1
10.10.100.9
```

After restarting the DHCP service and DHCP relay, PC2 successfully completed DHCP DORA and received an address from R1.

This troubleshooting process demonstrated that successful ping connectivity does not necessarily mean that the application or service itself is correctly configured. The DHCP logs were necessary to identify the actual failure.

## OSPF and DHCP Failover Testing

I then tested whether centralized DHCP would continue working if the direct R1-R3 connection failed.

Because the backup path would cause R1 to send DHCP traffic through its R1-R2 interface, I also configured the DHCP server to listen on:

```text
10.10.100.1
```

R1's DHCP listen addresses are now:

```text
10.10.10.1
10.10.100.1
10.10.100.9
```

R3 was also configured with both router-facing interfaces available to the DHCP relay:

```text
eth2 -> direct path toward R1
eth0 -> backup path through R2
```

I then temporarily disabled the direct R1-R3 link.

Before the failure, R3 reached R1 using:

```text
R3 -> R1
OSPF metric: 2
```

After the failure, OSPF automatically reconverged and changed the path to:

```text
R3 -> R2 -> R1
OSPF metric: 3
```

R3 was still able to ping `10.10.10.1`.

I then forced PC2 to request another DHCP lease.

PC2 successfully completed DORA and received:

```text
IP Address:  10.10.20.100/24
Gateway:     10.10.20.1
DHCP Server: 10.10.10.1
```

This confirmed that DHCP relay continued to work through the backup OSPF path.

I restored the R1-R3 link afterward. OSPF reconverged again and returned to the lower-cost direct R3-R1 path.

DHCP continued to work normally after restoration.

## Final Result

The lab now supports:

- Centralized DHCP
- Multiple DHCP scopes
- DHCP relay across routed networks
- OSPF dynamic routing
- Redundant router paths
- Automatic OSPF reconvergence
- DHCP service continuity during a link failure
- DHCP service restoration over the preferred path
- DHCP troubleshooting using VyOS/Kea logs

The final DHCP architecture is:

```text
                    R2
                   /  \
                  /    \
                 R1----R3
                 |      |
                PC1    PC2

R1
Central DHCP Server
├── 10.10.10.0/24
└── 10.10.20.0/24

R3
DHCP Relay for PC2 LAN

R2
Transit router used during OSPF failover
```

This milestone showed how DHCP relay and dynamic routing can work together to provide centralized network services while maintaining connectivity during a routing-path failure.
