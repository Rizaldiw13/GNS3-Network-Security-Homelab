# Project Log - August 25, 2026

## OSPF Redundancy and Failover Milestone

Today I expanded the existing three-router OSPF topology by adding a redundant link between R1 and R3.

The goal was to create an alternate network path and verify that OSPF could automatically recalculate its routes when the preferred path failed.

## Starting Topology

Before adding redundancy, the router topology was linear:

```text
PC1 --- R1 --- R2 --- R3 --- PC2
```

OSPF was already configured on all three routers in Area 0.

Router IDs:

- R1: `1.1.1.1`
- R2: `2.2.2.2`
- R3: `3.3.3.3`

The existing transit networks were:

- R1-R2: `10.10.100.0/30`
- R2-R3: `10.10.100.4/30`

## Adding a Redundant Transit Link

I added a direct link between R1 and R3 using their `eth2` interfaces.

The next available `/30` subnet from the transit address pool was `10.10.100.8/30`.

Address allocation:

- Network ID: `10.10.100.8`
- R1 eth2: `10.10.100.9/30`
- R3 eth2: `10.10.100.10/30`
- Broadcast: `10.10.100.11`

The new topology became:

```text
                 R2
                /  \
               /    \
              R1----R3
              |      |
             PC1    PC2
```

## R1 Configuration

```text
set interfaces ethernet eth2 address '10.10.100.9/30'
set protocols ospf interface eth2 area 0
```

## R3 Configuration

```text
set interfaces ethernet eth2 address '10.10.100.10/30'
set protocols ospf interface eth2 area 0
```

After committing the configurations, I verified direct connectivity across the new transit network.

R1 successfully pinged `10.10.100.10`.

R3 successfully pinged `10.10.100.9`.

Both interfaces showed an `u/u` state.

## New OSPF Adjacency

After enabling OSPF on both `eth2` interfaces, R1 formed a new OSPF adjacency with R3.

R1 now had two OSPF neighbors:

```text
2.2.2.2 -> R2
3.3.3.3 -> R3
```

Both neighbor relationships reached the `Full` state.

The OSPF topology was now:

```text
                  2.2.2.2
                     R2
                    /  \
                   /    \
                  /      \
             R1 ---------- R3
          1.1.1.1       3.3.3.3
```

All links remained in OSPF Area 0.

## OSPF Path Selection

Before adding the R1-R3 link, R1 reached the PC2 LAN through R2 and R3:

```text
R1 -> R2 -> R3 -> 10.10.20.0/24
```

The OSPF route had a cost of 3.

After adding the direct R1-R3 link, R1 automatically selected the shorter path:

```text
R1 -> R3 -> 10.10.20.0/24
```

The routing table showed:

```text
O>* 10.10.20.0/24 [110/2] via 10.10.100.10, eth2
```

This reduced the OSPF cost from 3 to 2.

No static route was configured. OSPF automatically recalculated the shortest path after learning about the new topology.

## Traceroute Before Failure

From PC1, traceroute to PC2 showed:

```text
1  10.10.10.1
2  10.10.100.10
3  10.10.20.10
```

This confirmed the active path:

```text
PC1 -> R1 -> R3 -> PC2
```

## Simulating a Link Failure

To test OSPF failover, I administratively disabled R1's `eth2` interface:

```text
set interfaces ethernet eth2 disable
```

I committed the configuration but intentionally did not save it because the failure was temporary.

The interface state changed to `A/D`:

- `A` = Administratively Down
- `D` = Link Down

This removed the direct R1-R3 path.

## OSPF Neighbor Change

After disabling `eth2`, R1 lost its direct adjacency with R3.

R1's OSPF neighbor table now contained only:

```text
2.2.2.2 -> R2
```

This confirmed that OSPF detected the failed R1-R3 link.

## OSPF Reconvergence

After the failure, R1 automatically recalculated its route to the PC2 LAN.

The new route became:

```text
O>* 10.10.20.0/24 [110/3] via 10.10.100.2, eth1
```

The path changed from:

```text
R1 -> R3
```

to:

```text
R1 -> R2 -> R3
```

The OSPF cost increased from 2 to 3 because the alternate path required an additional routed hop.

No manual routing changes were required.

## Failover Verification

PC1 was still able to successfully ping PC2 while the direct R1-R3 link was down.

Traceroute showed:

```text
1  10.10.10.1
2  10.10.100.2
3  10.10.100.6
4  10.10.20.10
```

This confirmed the failover path:

```text
PC1 -> R1 -> R2 -> R3 -> PC2
```

End-to-end connectivity remained available despite the preferred link failure.

## Restoring the Preferred Link

I restored R1's `eth2` interface using:

```text
delete interfaces ethernet eth2 disable
```

After committing and saving the configuration, R1 automatically re-formed its OSPF adjacency with R3.

The routing table returned to:

```text
O>* 10.10.20.0/24 [110/2] via 10.10.100.10, eth2
```

Traceroute again showed:

```text
PC1 -> R1 -> R3 -> PC2
```

The ping reply TTL also changed from `61` during the three-router failover path to `62` after restoring the shorter two-router path.

## Result

This milestone demonstrated:

- Redundant Layer 3 connectivity
- OSPF neighbor formation
- OSPF shortest-path selection
- OSPF route cost changes
- Link-failure detection
- Dynamic route recalculation
- OSPF convergence
- Automatic failover
- Restoration of the preferred route
- End-to-end validation using ping and traceroute

The network maintained PC1-to-PC2 connectivity after losing the preferred R1-R3 path without requiring any manual route changes.
